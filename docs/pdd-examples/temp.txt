Claude Code Prompt — ProductFlow v2: Strategic + Execution Phases
Context
ProductFlow is my PM intelligence platform. Today it runs 7 "robots" (scout, detective, people, money, feature, plan, priority) that produce strategic product analysis. They answer "should we build this?" well but don't produce an execution-ready Product Definition Document (PDD).
I'm evolving ProductFlow to handle the full PM lifecycle — from market validation through to a ship-ready PDD — in one unified flow, under a two-phase model.
Known architecture (ground truth — confirm, don't rediscover)

Language: Vanilla JavaScript, Node.js ES Modules. No TypeScript.
MCP: Official @modelcontextprotocol/sdk (TS/JS SDK), not FastMCP.
Prompt pattern: Each robot is self-contained. Every robot class has its own analyze() method that builds its own JSON prompt payload with _claudeInstructions, mandate, requiredSections, outputFormat. There is no shared template system and you will not introduce one.
Persistence: File-based only. No SQLite, no Postgres.

Global: brain/brain-database.json (history, learnings, design prefs, feedback).
Per-product workspace: context/ (PM-provided context that robots consume) + assets/ (robot outputs as .md and .json).


UI: None. Output is an HTML presentation in /plans/ or markdown/JSON in product workspace.
Directory layout:

src/ — mcp-server.js + workspace logic
robots/ — one file per robot (e.g., scout-robot.js)
leader/ — team-leader.js orchestrator
brain/ — brain-database.js + learning-engine.js
utils/ — I/O, prompt formatting, keyword extraction, presentation wrappers
plans/ — final HTML artifacts

Architectural constraints — non-negotiable

One product, two phases, one workspace. Phase is a status field. No separate product types, no duplicate storage.
Phase 2 robots read from both context/ and assets/ at runtime. context/ holds the PM-provided product context (the same source Phase 1 robots read). assets/ holds Phase 1 robot outputs (the new inputs Phase 2 robots build on). Phase 2 robots never re-prompt the PM for anything already captured in either folder.
Phase gating. PM cannot run a Phase 2 robot until N Phase 1 robots are complete. Recommend N in the Discovery Report; defend it.
Backwards compatibility. Existing products, existing Phase 1 MCP tool signatures, existing file layouts, existing team-leader.js flows — none may break. Add, don't rewrite.
MCP-native. New robots register as MCP tools through src/mcp-server.js the same way existing ones do. No new server process, no new transport.
Self-contained prompts per robot. Do not introduce a shared template engine. Each new robot follows the existing analyze() pattern — self-contained payload with _claudeInstructions, mandate, requiredSections, outputFormat.
Real LLM calls. Per the robot-reviewer skill — no static placeholder output. Every robot calls Claude via the API with product context.
Prompt hygiene. System prompts follow /mnt/skills/user/productflow-prompt-engineer/SKILL.md. Output schemas follow /mnt/skills/user/productflow-analyst/SKILL.md. Robot code reviewable under /mnt/skills/user/productflow-robot-reviewer/SKILL.md.
Learning loop from day one. Every new robot plugs into brain/learning-engine.js — ratings, feedback, prompt adaptation — the same way existing robots do. Not retrofit later.
JSDoc all inputs and outputs. Vanilla JS gives no type safety; JSDoc comments on every robot's input context and output schema are mandatory. The composer depends on field shapes being predictable.
Composer hits the PDD JSON schema exactly. See schema below. Fields may be null/empty if a robot hasn't run, but the shape is fixed.
